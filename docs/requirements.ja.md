## 1. プロダクトコンセプトとビジョン

**コンセプト**:
「チャットを捨て、片手親指のスワイプだけで無数の自律型エージェントを監督・承認する、
モバイルファーストな Human-in-the-Loop（HITL）インターフェース」

- **コアターゲット**: 複数の長時間実行エージェント（リサーチ、コーディング、業務自動化、
  顧客対応など）を常時走らせているパワーユーザーおよびエンジニア。
  移動中やスキマ時間に「エージェントの判断待ち（Needs Input）」を素早く安全に処理したいユーザー
- **設計哲学**:
  - **0msレイテンシ（Optimistic UI）**: サーバーの応答を待たずに指の動きに合わせて画面が次へ遷移する
  - **Diffファースト**: 長文の思考ログは隠し、「何がどう変更されるか」の差分と信頼度だけを1秒で把握させる
  - **安全な動的生成（A2UI準拠）**: コード実行を排除した宣言的JSONにより、
    安全かつデザインシステムに統一された動的フォームを展開する

## 2. 既存ソリューションに対する構造的比較優位

| 比較軸 | Slack / Telegram（チャット型） | Pushcut（通知拡張型） | 一般的なA2UI実装例 | 本プロダクト（AgentDesk Mobile） |
|---|---|---|---|---|
| 画面構造 | 過去ログが流れる時系列タイムライン | OS標準の通知履歴リスト | 単一のチャット埋め込み画面 | 未処理タスクのみが積まれるカードスタック |
| トリアージ操作 | 小さなインラインボタンを目視でタップ | 通知長押し → アクション選択 → フォーム入力 → 送信ボタン | フォーム入力 → 送信ボタン | 親指1本のスワイプ操作（左右・上下ジェスチャー） |
| 情報提示 | 長文テキストで画面が埋もれる | タイトルと本文のみ（表現力不足） | 画面全体を再描画 | 要約Diff ＋ 信頼度スコア ＋ 必要時のみ動的フォーム |
| OS統合 | バナー通知のみ | リッチプッシュのみ | なし（アプリ内のみ） | iOS Live Activities / Dynamic Island 直結 |
| 二重実行防止 | 過去メッセージのボタン誤爆リスク | なし（端末依存） | クライアント実装任せ | 使い捨てNonceと分散ロックによる厳格な排他制御 |

## 3. UI/UXデザイン要件

### 3.1 カードスタック型トリアージ（メイン画面）

**インターフェース構造**: 画面中央にエージェントからの要請カードがトランプの山札のように
重なって表示される（最前面の1枚に集中させる構造）。
残りタスク数がヘッダーにバッジ表示される（例：「5 pending」）。

**ジェスチャー設計**:

- **右スワイプ（Approve）**: エージェントの提案を即座に承認し、処理を続行させる。
  カードは右へ飛び、触覚フィードバック（軽快なHaptic）が鳴る
- **左スワイプ（Reject / Dismiss）**: 提案を拒否、または通知を破棄する。カードは左へ飛ぶ
- **上スワイプ / タップ（Inspect & Modify）**: 下部からハーフモーダル（ボトムシート）が展開し、
  詳細なパラメータ修正フォームまたは思考プロセスを表示する
- **下スワイプ（Snooze）**: タスクを山札の最後尾へ回す、または指定時間後に再通知する

### 3.2 視覚的情報設計（カード面の構成）

カード1枚の情報量は極限まで圧縮し、以下の順序で配置します。

1. **ヘッダー**: 送信元エージェントのアイコン、エージェント名、経過時間、重要度バッジ
2. **AI信頼度インジケーター**:
   - `Confidence: 98%`（高信頼：緑）→ ユーザーは無思考で右スワイプ可能
   - `Confidence: 62%`（要確認：黄/赤）→ 注意深く確認すべき理由をタグ表示
3. **Diff（差分）ハイライト表示**:
   「カレンダー予約：14:00 → 16:30」「Stripe返金：$120.00 → 対象：UserA」
   赤・緑の差分ハイライトを用いて、変更内容を0.5秒で把握可能にする
4. **クイック入力チップ（Chips）**: スワイプ以外の選択肢
   （例：「別の日程を提案」「金額を半額にする」）をタップ可能なチップとして下部に配置

### 3.3 コンテキストに応じた動的フォーム展開（ボトムシート）

エージェントが「ユーザーの微調整」を求めている場合、A2UIカタログに基づいた
ネイティブコンポーネントがボトムシート内に動的描画される。

- **使用可能コンポーネント**: 数値スライダー、日付時刻ピッカー、セグメント切り替え、
  音声/テキスト入力フィールド
- **送信アクション**: ボトムシート内の「修正して承認」ボタンを押すと、
  入力データのみがエージェントへ返送される

### 3.4 iOS Live Activities / Dynamic Island 連携

- 長時間稼働するエージェント（バックグラウンド処理）の進行状況をロック画面や
  Dynamic Island に常駐表示
- 「承認待ち（Needs Input）」状態へ遷移した瞬間、Dynamic Island が展開し、
  ロック画面上に「Approve / Reject」のボタンが直接表示される
- ユーザーはアプリを起動することなく、ロック画面の Face ID 認証とワンタップのみで
  エージェントを再開できる

## 4. 機能要件（Functional Requirements）

### 4.1 プロトコル受信＆パース要件

- **FR-1.1**: Server-Sent Events（SSE）またはWebSocket接続を常時確立し、
  エージェントサーバーからのA2UIメッセージ（JSON Lines）をリアルタイム受信すること
- **FR-1.2**: 受信したA2UIスキーマ（createSurface, updateComponents, updateDataModel）を
  パースし、ローカルのコンポーネントカタログに適合するネイティブウィジェット
  （Flutter Widget / SwiftUI View）へ動的マッピングすること
- **FR-1.3**: 未定義のコンポーネントやスキーマ破壊が含まれていた場合、
  アプリがクラッシュすることなくフォールバック用の汎用テキストカードとして安全に描画すること

### 4.2 トリアージ判定＆アクション送信要件

- **FR-2.1**: スワイプまたはボタン操作が行われた際、クライアント側で0msで
  アニメーションを完了させ、タスクスタックから即座に取り除くこと（楽観的UI更新）
- **FR-2.2**: ユーザー操作の結果（actionId, actionName, contextData）を
  バックエンドのエージェントWebhook/RPCエンドポイントへ非同期送信すること
- **FR-2.3**: オフライン時に操作された場合、ローカルキューに保持し、
  ネットワーク再接続時に順次送信すること

### 4.3 状態管理＆マルチデバイス競合制御

- **FR-3.1**: 各カードデータにはユニークなtaskIdおよびワンタイムのnonce
  （使い捨て実行トークン）を付与すること
- **FR-3.2**: デスクトップ側（PCブラウザ等）ですでに処理されたタスクについては、
  SSE経由でdismissTaskイベントを受信し、モバイル側のスタックから
  アニメーションを伴って自動消去すること
- **FR-3.3**: 同一タスクに対する二重送信（モバイルとPCの同時承認など）が発生した場合、
  バックエンド側で楽観的ロックにより片方を拒絶し、端末側に「処理済み」トーストを表示すること

## 5. 非機能要件（Non-Functional Requirements）

### 5.1 応答性・パフォーマンス

- **NFR-1.1（フレームレート）**: カードスワイプおよびボトムシート展開のアニメーションは、
  常時60fps（ProMotion対応端末では120fps）を維持すること
- **NFR-1.2（コールドスタート）**: アプリ起動から最初のカードスタックが表示されるまでの時間を
  500ms以内とすること（ローカルキャッシュの先行表示）

### 5.2 セキュリティ・サンドボックス

- **NFR-2.1（コード実行の排除）**: エージェントから送信されるペイロード内にHTML文字列や
  JavaScriptコードが含まれていたとしても、それを実行・評価するWebViewやeval機構を
  一切排除し、純粋なデータとしてのみ扱うこと
- **NFR-2.2（間接プロンプトインジェクション対策）**: カード内に表示される外部由来のテキスト
  （メール本文、PRコメント等）は、システムUIの装飾タグと明確に分離されたスタイル
  （引用ブロック形式等）で描画すること
- **NFR-2.3（実データの分離）**: 機微な認証情報や大量のマスターデータはA2UIスキーマ内に含めず、
  クライアントが保有する短命のベアラートークンを用いて安全なエンドポイントから
  個別フェッチする設計とすること

## 6. システムアーキテクチャ＆推奨技術スタック

システム全体は「エージェント（送信元）」「通知中継ハブ（バックエンド）」
「モバイルクライアント（受信側）」の3層で構成します。

- **モバイルクライアント**: Flutter（推奨）
  - 理由: Google公式の `package:genui`（A2UI対応SDK）が提供されており、
    1つのコードベースでiOS / Android双方の高品質なネイティブ描画が可能
  - スワイプスタック実装: `flutter_card_swiper` パッケージを統合
  - iOSネイティブ拡張: Live Activities / Dynamic Island のレンダリング用に
    Swift / WidgetKit をMethodChannel経由で連携
- **バックエンド（通知中継ハブ）**: Cloudflare Workers + Durable Objects
  - 理由: 極めて低いコールドスタートレイテンシ、エッジでのWebSocket/SSEコネクション維持、
    Durable Objectsによるタスク状態の一元排他ロック
  - プッシュ通知配信: APNs および FCM をWorkersから直叩き
- **エージェント連携インターフェース**: 外部ツール（LangGraph、Dify、Claude Code、n8n、
  カスタムエージェント）向けに、シンプルなWebhook URL（`POST /api/v1/tasks`）を提供

## 8. 実装ロードマップ

### フェーズ 1: 最小動作プロトタイプ（MVP）

- FlutterによるカードスタックUI（左右スワイプ操作のみ）の実装
- Cloudflare WorkersでWebhookを受け取り、SSEでスマホへプッシュする基本パイプラインの構築
- スワイプ判定がエージェントのコールバックURLに正しく届くことの検証

### フェーズ 2: A2UI動的フォーム＆Diffコンポーネント対応

- Google genui パッケージを統合し、上スワイプ時にボトムシート内で
  A2UIフォーム（日付、数値、選択肢）を描画可能にする
- Diff表示コンポーネント（変更前後ハイライト）および信頼度スコア表示の実装
- 楽観的ロックと使い捨てNonceによる二重承認防止ロジックの実装

### フェーズ 3: OS統合＆マルチデバイス同期

- iOS WidgetKitと連携し、Live Activities / Dynamic Island からのワンタップ承認を実装
- Webブラウザ版トリアージUIの作成およびWebSocketによるPC・スマホ間の即時状態同期
