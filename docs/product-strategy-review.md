# AgentDesk のプロダクト戦略レビュー

> 2026-10-06 時点のリポジトリ内資料に基づく戦略仮説。市場規模、競合の実測、顧客インタビュー、利用データは調査していない。以下の市場・採用に関する記述は、明示しない限り検証前の仮説である。

## 結論

**構造的な見直しは必要。ただし、中心は「スワイプUIを捨てる」ことではない。**

AgentDesk はすでに、カードUIだけでなく Web UI、共通ハブ、アクションの楽観ロック、Undo、期限付き処理を持つ。既存の強みは「人の注意を節約しながら、安全にエージェントの判断待ちを処理する」ことにある。ところが、README の表現と開発計画はなお「無数のエージェントをスマホでスワイプする」体験と機能追加に重心を置いている。顧客が買うのはスワイプではなく、**既存のエージェントに簡単につながり、誤承認せず、判断結果が確実に返る運用**である。

次の戦略的単位を「モバイルアプリの機能」から **特定の承認ワークフローを本番運用できる、エージェント非依存の承認レイヤー**へ移す。まず対象を狭くし、接続・判断・実行結果の一連の価値を実証する。Live Activities、ジェスチャーの追加、汎用的な Fleet 管理は、その実証の後に置く。

## 現状の強みとギャップ

### すでにある土台

- Hub が pending / processed 状態の正本となり、SSE と snapshot で Web・Mobile に配信する。nonce による二重処理防止、オフラインキュー、Undo 猶予、期限処理も実装済みと記載されている（`docs/architecture.md` §Flows、`TODO.md` Done）。
- Mobile と Web の両方で判断できる。したがって価値を「スマホ専用」に狭める必要はない（`docs/architecture.md` §Phase 2 status）。
- 純粋なデータ描画、外部テキストの分離、危険度に応じた確定の重さは、安全な承認体験の核となる（`docs/philosophy.md` P2/P5/P7）。
- Hub への `POST /api/v1/tasks` と `replyUrl` 返送により、独自UIを持たないエージェントにも接続できる基本契約がある（`docs/architecture.md` §Enqueue/Triage）。

これらは「意思決定の受信箱」を作る要素であり、単なる通知ビューアより強い。ただし、リポジトリ上の機能記述は、実利用者・本番導入・顧客成果の証明ではない。

### 採用を止めるギャップ

1. **初回接続の価値が弱い。** Quickstart は開発者向けのローカル3ターミナル構成で、実ユーザーのエージェントをつなぐ最短手順や、既存ワークフローへ戻るまでの時間は示されていない（`README.md`）。独自のWebhook契約を使えることと、「主要なエージェントにすぐ接続できる」ことは別である。
2. **誰の、どの損失を減らすかが広すぎる。** 要件は調査・コーディング・業務自動化・顧客対応を並べ、「数個〜数十個のエージェント」を想定する（`docs/requirements.ja.md` §1、`docs/philosophy.md` 前提）。複数エージェントを常時使う層は狭い可能性があるうえ、用途ごとに承認に必要な証拠・失敗コスト・監査要件が異なる。[仮説]
3. **意思決定の根拠に関する約束が不揃い。** `README.md` は「信頼度スコア」を訴求する一方、`docs/design-philosophy.md` §原則1はエージェント自己申告の confidence をカード表から排除するとしている。自己申告確率は承認判断の根拠として弱く、ここは README の訴求を直し、観測・校正された根拠がない数値を表示しない方針に統一するべきである。
4. **「速い判断」と「良い判断」が混同される危険。** 0.5秒で理解、0ms UI、受信箱を空にする、という表現は体験目標としては分かるが、ユーザーが急いで承認すること自体を価値にしてはいけない。哲学文書の注意資源・リスク連動摩擦とは緊張がある（`docs/philosophy.md` P2/P4/P8）。成功は速度単独でなく、誤承認・再作業・割り込みの減少で測るべきである。
5. **安全なデモと本番導入の距離がある。** Architecture は現在の `AGENT_TOKEN` / `CLIENT_TOKEN` を長期トークンとし、端末ごとの短期トークン等を将来課題として記載している（`docs/architecture.md` §Security）。単一の global DO という構成も現行アーキテクチャに記載がある（同 §Why a single Durable Object）。これは試作の欠点と断定するものではないが、顧客データ・複数組織・監査を扱う製品として売る前に、テナント分離、資格情報、データ保持、監査・復旧、運用責任を明示して設計検証する必要がある。
6. **モバイルが常に最適な承認場所とは限らない。** 外出時の利便性は価値になり得る一方、重要操作を移動中に促す設計は、集中・アクセシビリティ・安全性と衝突する。移動中に判断を急がせず、緊急度と期限で通知を制御し、詳細な検証は Web でも完結させるべきである。

## 競争軸を置き直す

| 代替 | ユーザーがすでに得ているもの | AgentDesk が証明すべき差 |
|---|---|---|
| Slack / Teams / Discord の通知・承認ボタン | 導入済みの会話・通知基盤、チームの習慣 | 判断待ちの見落とし・重複・文脈探しをどれだけ減らすか。チャットを置き換えるのではなく、承認の状態と結果を構造化する価値 |
| エージェント提供元の承認画面・IDE内UI | ツール固有の情報と承認フロー | 複数エージェントを跨いだ一貫した承認、端末間同期、安全な決定履歴 |
| 独自ダッシュボード／Webhook | 既存業務に合わせた自由度 | 新しい画面を作らずに利用可能な連携の簡単さと、信頼できる共通の決定状態 |
| OS通知 | すぐ気づける入口 | 通知を見ただけでなく、根拠を確認・修正し、重複なく決定し、結果まで追跡できること |

比較対象の機能差は仮説であり、競合の最新機能を網羅的に調査した結果ではない。勝ち筋は「スワイプはSlackより速い」と主張することではなく、**承認の状態遷移と結果返送を既存の通知より確実にすること**にある。

## 市場・顧客ニーズの仮説

### 需要が生まれる条件

AgentDesk の需要は「AIエージェントが増える」だけでは生まれない。次の条件が同じ利用者に揃う必要がある。

1. エージェントが、人の許可なしには先へ進めない具体的な判断を繰り返し生む。
2. その待ち時間が、担当者の中断、処理遅延、エージェント稼働率の低下のいずれかとして顕在化している。
3. 既存の通知先・承認画面では、要求が埋もれる、必要な差分が見えない、返答後の状態が分からない、という継続的な不都合がある。
4. AgentDesk を導入する方が、通知連携・権限設定・運用教育・新しい画面の切り替えにかかる費用より得である。

この条件がなければ、ユーザーは既存のチャット通知やエージェント内承認で十分と判断するはずである。従って「エージェント数」ではなく、**人間が処理している承認待ちの頻度・損失・既存手段の限界**を市場の出発点にする。

### 世界市場に関する外部シグナル

世界的に、エージェントの普及と「どこまで自律させるか」の間にギャップがある。これは人間の監督・承認機能が不要ではないことを示すが、AgentDesk のような独立したモバイル受信箱への支払需要を直接証明するものではない。

- Gartner の2025年調査では、北米・欧州・アジア太平洋の従業員250人以上の組織におけるITアプリケーション責任者360人のうち、75%が何らかのAIエージェントを試験・導入中または導入済みと回答。一方、監督不要の完全自律エージェントを検討・試験・導入している割合は15%、自組織に適切なガバナンスがあると強く同意した割合は13%だった。**[Gartner, 2025-09-30](https://www.gartner.com/en/newsroom/press-releases/2025-09-30-gartner-survey-finds-just-15-percent-of-it-application-leaders-are-considering-piloting-or-deploying-fully-autonomous-ai-agents)**。Gartner本文は本調査環境から取得できず、数値は同社のプレスリリース検索結果に基づく。
- EY の2025年米国AI Pulse調査では、経営幹部500人の34%がAgentic AIの実装を開始したと回答し、89%が人間の介入は今後も重要と回答。これは**米国の経営層調査**であり、世界の一般ユーザーを代表する統計ではない。**[EY, 2025-07-29](https://www.ey.com/en_us/newsroom/2025/07/ai-investments-surge-but-agentic-ai-understanding-and-adoption-lag-behind)**。
- 承認ゲートは抽象的な構想だけではない。Anthropic の Claude Code は非対話モードで MCP permission-prompt tool を使い、通常の設定で決まらないツール実行許可を外部ツールへ委ねる仕組みを提供している。これは「エージェントの動作を人間に確認する」課題が実際の開発者ワークフローに現れている証拠である一方、プラットフォーム内蔵機能やその周辺統合が直接の代替になる証拠でもある。**[Anthropic Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference#cli-flags)**。

したがって、**世界の中にニーズがあるか**への判断は「はい。ただし、より広い agentic workflow の監督・制御ニーズがあるという意味」である。現時点で強く言えるのは、人間の監督を残したエージェント導入が実際に進んでいること。まだ証明されていないのは、そのニーズを独立したハブで満たすべきこと、複数ベンダー横断の必要性、スマートフォンが最良の承認面であること、そして顧客がそれに費用を払うことである。必要なのは架空の「TAM」ではなく、その広い波の中から AgentDesk の形が解く具体的な高頻度問題を見つけることだ。

### 顧客候補セグメント

| セグメント仮説 | いまの困りごと | 導入動機 | 主な障壁 | 初期優先度 |
|---|---|---|---|---|
| 個人開発者・エージェントのヘビーユーザー | 複数の実験的エージェントの許可待ちが端末やチャットに散らばる | 低コストで試せる。ひとりで判断・導入できる | 承認待ちの量が少ない可能性。自前Webhookも代替になる。支払意思が弱い可能性 | **学習用に高め**。実装者を早く見つけやすいが、企業需要の代用にはしない |
| 小規模チームの開発・運用担当 | コーディング／運用エージェントの変更・デプロイ承認がIDE、PR、チャットに分散 | 待ち時間、担当者不在、変更影響、誰が承認したかを揃えたい | IDE／Git管理製品に承認が内蔵される。誤デプロイ時の責任と監査の要求 | **第一候補の検証対象**。イベントが具体的で、実行結果まで追いやすい。現状の第一市場と断定はしない |
| ノーコード自動化・業務自動化の運用者 | n8n / Dify 等の人手待ちステップが遅延し、運用画面を見張る必要 | 承認待ち通知と再開を簡単にし、モバイルから確認したい | プラットフォーム標準機能との差が小さい可能性。各フローのデータ形式がばらばら | **統合のしやすさを試す候補**。一つのプラットフォームに限定した試作で評価 |
| 企業の AI ガバナンス／セキュリティ担当 | 複数のエージェントが業務システムを操作する際の権限、承認記録、監査 | 最小権限、職務分離、証跡、ポリシーを一元化したい | SSO、RBAC、監査、保持、テナント境界、SLA、調達審査が必要。現行プロトタイプとの差が大きい | **短期の第一市場にはしない**。強い需要が確認されても製品・運用基盤の再設計が必要 |
| 顧客対応・金銭・予約等の業務オペレーション | 返金、送信、変更などをAI提案の後に人が確認する | 高頻度な処理、ミス削減、制御可能な委任 | 個人情報、誤判断の損害、業務システム連携、誤った要約への依存 | **重大な実証が必要**。コスト高・責任の重さに見合う証拠と業務パートナーなしに選ばない |

初期には **個人・小規模チームの開発ワークフロー**を並行して聞き、最も強い実例を選ぶのが妥当な仮説である。ユーザーを見つけやすい開発者向けは学習市場として優れる可能性がある一方、そこにおける「面白い」利用が継続利用・支払意思・企業向け需要を意味するとは限らない。企業ガバナンスを先に掲げると、現行アーキテクチャにない運用保証まで約束する危険がある。

### ユーザーの本当の仕事（Jobs to be Done）

- **担当者として**：エージェントを止めず、必要な瞬間だけ安全に判断し、自分がいない時間の滞留を減らす。
- **承認者として**：提案の結論ではなく、変更対象・影響・可逆性・根拠を必要十分に確かめ、誤りなら止める。
- **運用責任者として**：誰が何を判断し、エージェントがその後どうしたかを後から説明する。
- **導入担当として**：新しいプラットフォーム移行なしに、既存のエージェント／Webhookへ最短でつなぎ、失敗時に安全に切り戻す。

機能価値は、カード表示やスワイプ単体より、この4つの仕事のうちどれを先に確実に果たすかで評価する。ユーザーが欲しいのは「AIを監督している感覚」ではなく、仕事を止めずにリスクを管理することだと仮定する。

### 市場の形と販売仮説

- **需要の時間軸**：汎用的な「数十エージェントの受信箱」は、エージェントの普及と承認待ちの集積が進まないと日常必需品にならない可能性がある。逆に、特定の高頻度な承認工程に埋め込めば、エージェント数が少なくても価値が出る可能性がある。[仮説]
- **競争の形**：直接の類似アプリだけでなく、各エージェントの組み込み承認、Slack等のワークフロー、Webhookを使った自社実装が代替になる。既存ツールが承認を十分に構造化した場合、「中央集約UI」自体が不要になるリスクがある。
- **支払者と利用者**：開発者向けでは同一人物が導入と利用を兼ねやすい。企業では承認者、運用チーム、セキュリティ、予算保有者が異なる可能性があり、利便性だけでは購入されない。実ユーザーと購入意思決定者を分けて調査する。
- **販売経路**：最初は一人で試せる開発者向けサンプル／Webhook連携が学習速度を上げる可能性が高い。その後、チーム共有・監査・権限が強い要求として繰り返し現れた場合に、チーム製品へ移行する。エンタープライズ販売を前提に先行投資しない。
- **市場規模**：この資料から信頼できる TAM / SAM / SOM は算出できない。利用可能なエージェント数や市場レポートから金額を置くのではなく、まず対象ワークフローの潜在顧客数、週次の承認件数、代替手段、予算保有者、導入転換率を調べる。狭い市場でも明確な痛み・反復利用・支払意思があれば、汎用市場を根拠なく主張するより強い初期事業仮説になる。

### 最初に検証する市場仮説

1. **頻度仮説**：「少なくとも週に複数回」人の判断待ちがあり、通知が散らばることが実際の遅延・中断になっているチームがいる。
2. **代替不満仮説**：既存のチャット／IDE内承認で問題が解消されない理由は、「通知がない」より「見落とす・根拠がない・返事の反映が分からない・担当者間で重なる」のいずれかである。
3. **接続仮説**：対象チームは、汎用APIドキュメントを読むより、特定の実例テンプレートを使うことで大きく早く導入できる。
4. **集中仮説**：全タスクを速く処理するのではなく、低リスクを効率化し、高リスクを検証に導くことで、割り込みと誤判断を同時に減らせる。
5. **支払意思仮説**：個人またはチームは、削減できる待ち時間・運用工数・失敗コストの一部を、継続利用または有償導入として差し出す。

### 仮説の検証方法

- まず 10〜15 人程度の候補者に最近の具体例をインタビューする。これは統計的な市場規模調査ではなく、問題と語彙を発見するための探索数である。一般的なAIへの好意ではなく、直近の判断待ち1件を入口から終端まで再構成する。
- **顕在需要の証拠**：過去1か月分の実際の承認待ちを見せてもらえる、既存ワークフローを共有する、設定時間を確保する、他の担当者を紹介する、または利用・支払の約束をすること。称賛や「使いたい」は弱い証拠として扱う。
- 3〜5 チームで、手作業でもよい concierge pilot を行う。週次の要求数、発生元、気づくまでの時間、決定に要した時間、判断根拠、保留・誤判断・再作業、コールバック成功、導入・保守時間を記録する。
- 既存手段と AgentDesk の試用を同種の判断で比較する。単純な前後比較では案件難度や慣れが混ざるため、可能なら同一チーム内で同じカテゴリの処理を比較し、件数の少なさ・観察期間を結果の制約として報告する。
- 「通知の追加でかえって中断が増える」「カード情報だけで正しく判断できない」「既存ツールの設定の方が容易」「週次の承認件数がほぼない」が観測されたら、そのセグメント／価値提案を棄却する。機能を足して仮説を温存しない。


## 推奨する構造的変革

### 1. 「何でも扱うUI」ではなく、最初の業務を一つ選ぶ

候補はコード変更・デプロイ承認、外部送信前のレビュー、金銭・顧客データを伴う操作など。いずれも例示で、現時点の選定結論ではない。利用者インタビューで、頻度・失敗時損害・既存の承認手段・自動化主体・支払意思を比較して選ぶ。

初期の楔（wedge）は、以下を満たす一つのワークフローとする。

- 週に何度も起き、担当者が現在は通知・チャット・手動確認で処理している。
- 何を承認するかを構造化でき、結果・可逆性・期限・差分を正確に提示できる。
- 対象ユーザーを10人前後、協力する開発者／運用者を数人見つけられる。
- 事故を防ぐ必要はあるが、AgentDesk の現状機能だけでは満たせない法規制・監査保証を前提としない。

### 2. 中核を「カード」ではなく「承認契約」に置く

一件の判断について、**発生元 → 提案と影響 → 人間の決定 → エージェントへの返送 → 実行結果**を通す。既存の task protocol をこの価値の土台として保ちながら、プロダクト契約として最低限必要な情報（実行対象、変更内容、可逆性、期限、決定後の状態、失敗時の扱い）をワークフロー別に明確にする。

新たな自由形式・巨大な汎用スキーマを先に作るのではなく、選んだユースケース一つで必要項目を定義し、実際のエージェント接続で不足を確かめる。UIはその契約の最適な表示手段の一つとし、スワイプは素早い低リスク判断に使い、高リスク判断は確認・根拠・保留を許す。

### 3. Slack／IDE を置き換えず、入口と戻り先にする

最初の価値を、ユーザーの既存環境にAgentDeskを追加するコストより大きくする。選んだ一つのエージェント／自動化経路に対し、入力テンプレート、Webhook設定例、具体的なサンプル、返信後の確認手順を揃える。導入の必須作業を測定し、数分で試せないなら統合を見直す。

Webは管理・精査、モバイルは通知・短時間の判断、といった役割分担を検証する。独立した第二の仕事場を強いるのではなく、元の仕事環境へ決定結果を返す。

### 4. 価値提案を「高速」から「安全に委任できる」へ

顧客向けの一文の案：

> **AIエージェントの承認待ちを一か所に集め、影響と取り消し可否を確認してから安全に返す。**

「どこでもスワイプ」「無数のエージェント」「0.5秒で判断」は、顧客検証後に補助的な体験説明として使う。速さは安全性と正確性の条件を満たした場合の便益であり、ユーザーに速い判断を強いる主張にしない。

## 優先順位

### P0 — 需要と導入経路を検証する

1. 3つ程度の候補業務について、対象者に最近の実例を聞く。「欲しいか」ではなく、直近の承認待ちの件数、処理時間、見落とし・差し戻し、現行の通知先、判断根拠、事故時の影響を聞く。
2. 最も痛みが強い一業務・一連携先を選び、エージェント送信から決定返送・実行結果までを動く試用で見せる。
3. 既存のSlack等との比較を同じタスク群で行い、処理時間だけでなく判断ミス・保留・再作業・通知負担を計測する。

**進行条件**：対象ユーザーが実データまたは実ワークフローで試し、複数人が週次で継続利用し、導入作業と明確な改善の両方が観測できる。閾値は最初の調査で事前に定め、結果を見て都合よく変更しない。

### P1 — 初回接続と信頼の摩擦を減らす

- ユースケース一つに絞った接続テンプレートとローカル／テスト用の安全な試用経路。
- 承認の監査可能性、エージェントへの返送失敗、期限切れ、競合、Undo後の状態をユーザーに理解可能にする。
- README と設計文書の矛盾を直す。README の confidence 表現を、`design-philosophy.md` の「自己申告confidenceを露出しない」と整合させ、実利用で裏付けられていない利点も削る。
- 本番導入の前提（トークン、テナント分離、保存・削除、監査、障害時の責任範囲）を明文化し、脅威モデルと必要な運用設計を評価する。

### P2 — 利用実績で必要性が出た機能だけを拡張

- サーバー側スヌーズ、通知制御・束ね、更新／取り下げは、対象業務で割り込みや重複が実際に問題なら優先する。
- SDK/MCP、複数アダプター、Live Activities / Push は、P0で選んだ顧客層の導入・応答率を明確に改善する場合に着手する。
- 新しいジェスチャー、グラフィック、Fleet、二人承認などは、それを必要とする実顧客とワークフローが確認されるまでは拡張しない。

## 成果の測り方

**North Star 候補：安全に完了した承認の割合**。分母を「AgentDesk に届いたすべての承認要求」とし、一定期間内に正しい判断が完了し、返送・実行結果が整合し、訂正・再実行・重大な競合を起こさなかった割合として定義する。各要素の定義と計測可能性は試用前に決める。

併せて測る指標：

- 連携設定から最初の成功した判断までの時間と、途中離脱点。
- 承認待ちの滞留時間、未処理・期限切れ・保留の比率。
- 誤承認、Undo、却下後のやり直し、コールバック失敗、重複処理の率。
- ユーザーあたりの通知数と、割り込みが不要だったと申告された通知の率。
- 同一タスク群における、既存手段との時間・ミス・やり直しの差。

「カード処理数」「スワイプ速度」「受信箱ゼロ」は単独の成功指標にしない。速く処理するほど誤判断が増えるなら、プロダクトは失敗である。

## 文書・実装の具体的な整合点

- `README.md` の confidence 訴求は `docs/design-philosophy.md` と矛盾。自己申告値を削除するか、計測・校正済みの根拠と意味を明確化するまで訴求しない。
- `README.md` の下スワイプ=snooze 表示は、現状がクライアントローカルであること（`docs/architecture.md` Known MVP deviations、`TODO.md` Next）を明記する。
- 「スマホ特化」「Web UIあり」「複数端末で同じ真実」の関係を整理し、モバイルを唯一の承認面として売らない。
- 要件原案の Dynamic Island / Push の表現と現在の Phase 3 未実装を混同させない。状態を製品紹介で区別する。
- 「何でも接続できる」より、検証済みの最初の統合を具体名と導入手順で示す。存在が確認できない専用プラグインや実績は主張しない。

## 判断

**プロジェクトを作り直す必要はないが、ロードマップの中心を入れ替えるべき。** 現在の TODO は undo・危険度・期限・返信信頼性など、基盤の安全性を伸ばす方向で哲学と整合している。一方で、これ以上の操作語彙や端末機能を優先する前に、誰が何のために接続し、使い続けるかを実証する必要がある。

最初の成果物は新機能ではなく、**一つの業務で「接続が簡単」「誤りに強い」「結果が戻る」を通しで証明する試用**である。その結果が弱ければ、UIを磨くのでなく、対象業務・統合の形・製品境界を変える。
