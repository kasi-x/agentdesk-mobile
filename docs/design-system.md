# AgentDesk Design System — 考察と方針

> AgentDesk の既存プロダクト思想を、Flutter・Web・将来の通知／ウィジェットで再利用できる視覚言語とコンポーネント規約に落とし込むための設計判断。画面の判断基準は [design-philosophy.md](design-philosophy.md)、プロダクトの価値基準は [philosophy.md](/docs/philosophy.md) を参照。

## 結論

AgentDesk のデザインシステムは、見た目を揃えるための部品集ではなく、**人の注意と判断の安全性を複数クライアント間で一貫して守るための意味体系**であるべき。共通にするのは色・余白のピクセル値だけでなく、「何を意味するか」「どの状態でどう振る舞うか」。各プラットフォームの表現はネイティブに保ちつつ、危険度、決定、同期状態、外部由来データの意味は同じにする。

現状の「暗い中立面＋意味に限定した色」「表は判断、詳細は根拠」という方向は、注意資源を節約し、複数エージェントの判断待ちを扱う本サービスに合う。一般的なブランド色主導のコンポーネント集や、全画面を同じカードで囲う設計は採らない。

### 目指す体験: 最小の入口、深い奥行き

利用者が求めるのは、**見た目も操作も最小構成でクール。それでいて、求めれば細部まで見られ、簡単な操作から高度な仕事まで自然に進められること**。情報や機能を削るのではなく、最初の画面で要求する注意を最小化し、必要な深さを即座に取り出せるようにする。

- 第一階層は目的と次の操作を絞って見せる。詳細は一貫した入口から開き、さらに高度な操作は文脈に沿って段階的に発見できるようにする。
- 高度な機能を「隠しジェスチャーを知る人だけの特権」にしない。基本操作はひと目で分かり、追加操作はラベル・配置・プレビュー・取り消しで安全に学べるようにする。
- ビジュアルの「クールさ」は情報量や装飾の多さで作らず、強い視線設計、精密なタイポグラフィ、意味のある色、応答性のよい動きで作る。
- シンプルさと表現力は両立させる。静かな待機状態から、操作・危険・変化の瞬間には色や動きが明確なシグナルとして立ち上がる。演出は理解と手応えを増やすために使い、判断を急かしたり隠したりしない。

## 1. 設計の基準

優先順位は次のとおり。

1. **判断の正確さと安全性** — 結果・影響・可逆性を誤読させない。高リスクほど明示的な確認と摩擦を持たせる。
2. **情報の優先順位** — まず「承認で何が起きるか」、次に必要な差分とリスク、最後に根拠・出典。詳細を必要な人だけが開ける。
3. **状態の真実性** — 楽観的UIを含め、送信中・確定・オフライン・競合・失敗を見た目だけで混同させない。状態の所有者はハブであり、クライアント上の一時状態を確定済みと装わない。
4. **操作可能性** — タッチ、キーボード、スクリーンリーダー等、入力方法が違っても同じ判断と結果に到達できる。スワイプだけを唯一の操作にしない。
5. **プラットフォームへの適合** — 意味と情報設計は共有し、ナビゲーション、フォーカス、システム設定への追従は各OS／Webの慣習を尊重する。

## 2. デザイン言語

### 色は装飾でなく意味

現在のWeb CSSとFlutter `PopColors` は、暗い中立背景・面、白系の文字、青系アクセントを共有し、緑・赤・橙などを状態や差分に使っている。この方向を基礎にする。ただし「色を控える」は色表現を弱くする意味ではない。色は普段は静かに保ち、リスク・選択・変化・確定など意味が立つ場面では、視認性と意味の一貫性を保ちながら大胆に使う。

色の役割は意味トークンとして定義する。少なくとも次の意味を区別し、同じ色を文脈ごとに別の意味で再利用しない。

- **背景／面／区切り**: 情報の階層を静かに作る。
- **操作アクセント**: フォーカス、選択、主要な中立アクション。
- **承認／成功、却下／破壊的操作**: 結果を示す。赤・緑だけで操作や意味を伝えず、文言・アイコン・形状も併用。
- **severity（info／warning／critical）**: リスクの強さ。承認・却下色とは別の意味軸として扱う。
- **同期／通信状態**: 未送信、処理中、確定、競合、失敗を区別する。severity色を流用して誤解させない。
- **外部由来コンテンツ**: システムUIから視覚的に隔離する。単に危険色を塗るのではなく、引用の形・ラベル・境界で文脈を伝える。

色は必ず文字・形・ラベルと組み合わせ、コントラストは実機・ブラウザで検証する。高リスクを色だけで区別しない。

### 余白・形・タイポグラフィ

- 余白は情報をグルーピングする主要な手段。装飾線や入れ子カードを増やす前に、間隔・面の差で階層を表す。
- 既存の角丸カードや面の高さは意味のあるコンテナに限る。すべての行・ラベルをチップや枠にしない。
- タイポグラフィは要約、影響額・日時、補足、メタ情報の順に明確な階層を作る。日本語での折返し、可変文字サイズ、長いエージェント名・外部テキストを前提にする。
- 金額・日時・差分など、値の種類に合った表現を優先する。等幅書体はコードや構造化差分など必要な範囲だけで使う。
- 密度の高い管理画面でも、一覧性のためにタップ領域や説明を削ってはならない。

## 3. トークンの構造と共有方法

トークンは **プリミティブ → セマンティック → コンポーネント** の三層で考える。

- **プリミティブ**: 色、寸法、文字サイズ、角丸、動きなどの値。製品の意味を持たせない。
- **セマンティック**: `surface`, `text-secondary`, `action-primary`, `severity-critical`, `sync-conflict` のような役割名。テーマやプラットフォームの差をここで吸収する。
- **コンポーネント**: `decision-card-surface` や `confirm-hold-target-size` など、その部品に固有の値。セマンティックトークンを参照し、必要なものだけ作る。

実装上は、Web の CSS custom properties と Flutter の `PopColors`／`ThemeData` が現在の対応する定義箇所である。値の二重管理はドリフトのリスクなので、新しい色や寸法を追加するときは両方の対応関係を更新し、名前と意味を揃える。現時点でトークン生成基盤を増やすより、まずこの意味対応を文書化し、変更時の同期を徹底する。両実装のずれや反復更新コストが継続的に問題になった時点で、単一ソースからの生成を検討する。手書き値を機械的に三層化するためだけの抽象化はしない。

テーマ追加は、実際の利用要求と意味色・コントラストの検証を満たした場合に行う。現行のダークテーマを無断でライトテーマへ広げず、将来テーマを追加する場合もコンポーネントが直接プリミティブ色に依存しない構造にする。

## 4. コアコンポーネントの契約

| 部品 | 見せるもの | 必須状態・振る舞い |
|---|---|---|
| 判断カード | 影響の要約、主要差分、危険度、必要な決定操作 | 通常／高リスク／期限切れ・無効／送信中／未同期。カード面に詳細を詰め込まず、誤操作時の取り消し・結果を明示する。 |
| 差分表示 | Before → After、変更対象に合う時間軸・金額・テキスト表示 | 追加・削除・変更を色だけで区別しない。長文・狭幅でも内容が欠落せず、外部入力を安全なテキストとして描画する。 |
| アクション | 具体的な動詞と、その結果・危険度に見合う確認 | フォーカス／押下／無効／処理中／失敗。破壊的操作は主操作と視覚・配置で明確に分け、危険に応じて追加摩擦を設ける。 |
| 詳細パネル | 判断根拠、出典、編集可能な値 | 展開／読み込み／空／エラー。カード面と同じ情報を無目的に重複せず、階層を深くしすぎない。 |
| 状態通知 | オフライン、同期中、競合、操作結果 | 一時的なトーストだけに依存しない。必要な状態は該当カードや一覧上にも残し、再試行・取り消しなど次の行動を示す。 |
| 外部引用 | 外部テキストとシステム指示の境界 | 引用元を区別し、長文を読みやすく折り返す。HTML／スクリプトとして解釈しない。 |

### 判断カードの標準レイアウト

モバイルの初期表示は、次の順序を標準とする。カードを開かずに通常の判断を完了でき、詳細を求めれば一段で検証・編集に進める。

1. **ヘッダー** — エージェント名、severityを示す小さな記号、判断に必要な場合だけ期限。エージェント名や時刻は主見出しより弱くする。
2. **影響の見出し** — 何が変わるかを短い文で示す。実行内容の説明だけでなく、ユーザーに起きる結果を主役にする。
3. **主要差分** — 日時なら時間軸、金額なら金額の前後、テキストなら変更箇所を強調。通常の差分は一目で比較できる密度に制限し、長文は詳細へ送る。
4. **決定操作** — 承認・却下・後で等を、画面下部の常に見つけられる操作領域にも置く。ラベルは実際の結果を表す動詞を優先する。
5. **詳細を見る** — 根拠、外部引用、出典、参加者、全期限、編集フォームなどを同じ入口から展開する。情報の種類に応じた次の操作は詳細内に置く。

期限切れ、高リスク、更新、同期失敗などのバナーは状態が発生した場合だけ出す。信頼度や説明を常時足して「充実している」ように見せない。緊急値は他の場所に重複表示せず、通常メタ情報は初期面から外す。

### ビジュアル基準値

次表は現在のCSS／Flutter実装に存在する値を基準値として明記したもの。大きく外す場合は、画面単位の気分で決めず、両クライアントのトークンと理由を一緒に更新する。

| 役割 | 基準値 | 適用 |
|---|---|---|
| 背景 | `#0A0A0B` | 画面のキャンバス |
| カード面 | `#1C1C1E` | 判断カード、主要面 |
| 内側の面 | `#2C2C2E` | 詳細内のまとまり |
| 主テキスト | `#FFFFFF` | 見出し、主要値 |
| 副テキスト | `rgba(235,235,245,.6)` | エージェント名、補足 |
| 控えめなテキスト | `rgba(235,235,245,.3)` | 非重要な時刻・補助情報。重要情報には使わない |
| アクセント | `#0A84FF` | フォーカス、詳細入口、主要な中立選択 |
| 承認・成功 | `#30D158` | 承認の結果・成功。色以外にもラベルと形で示す |
| 却下・破壊的操作／Critical | `#FF453A` | 同じ赤系でもsemantic roleは分離し、文言・形・アイコンを併用 |
| Warning | `#FF9F0A` | 要注意状態 |
| 強調色 | `#FFD60A` | 希少な注意喚起に限定。通常のseverityや承認色に流用しない |
| 中立fill | `rgba(120,120,128,.36)` / `rgba(120,120,128,.24)` | 選択・チップ等の薄い面。意味色の代替にはしない |

サイズの基準は4px刻みの余白群（4 / 8 / 12 / 16 / 20 / 24px）とする。主要画面で確認できる既存値は、モバイルのカード外側左右20px・内側12px・行間8px・角丸18px、Webカード幅上限440px・内側上下12px左右14px・行間8px。既存の差異はプラットフォーム適合によるものとして許容し、意味のない独自値を増やさない。

| 文字の役割 | 基準 | 使い方 |
|---|---|---|
| 影響見出し | 17px、Semibold、行高1.3（モバイル現行値） | カードの視線の起点 |
| 本文 | 15px、行高およそ1.47 | 説明・差分・詳細 |
| 補助ラベル | 12–13px、Medium以上 | エージェント名、時刻、状態。可読性を犠牲にする極小文字は禁止 |
| 数値 | tabular figures | 金額、カウントダウン、承認数の桁を揃える |

操作対象はタッチで押し分けられる面積を確保し、狭い画面・文字拡大時も見出しや決定操作を切り捨てない。タッチ領域は目安44×44px以上。カード上の動詞ラベルと下部の操作が競合する場合、同じアクションであることをアイコン・文言・操作結果で一致させる。

### 操作と動きの仕様

| 状況 | 操作 | 視覚・触覚の応答 |
|---|---|---|
| 通常カード | 右スワイプ＝承認、左＝却下、下＝後で。カードタップ＝検証ビュー（モバイルはInspect sheet）、明示的な「詳細を見る」＝詳細展開 | ドラッグに追従して方向と決定結果を示す。下部ボタンからも同じ判断ができる |
| 高リスク・不可逆 | スワイプ承認を無効化し、下部の長押しで確定 | 現行の1,200msリング充填を進捗として見せ、完了時に強い触覚を返す。指を離すと確定せず戻る |
| 詳細展開 | 「詳細を見る」をタップ | Flutter現行は260ms `easeOutCubic`、矢印は220ms。Web現行は280ms spring展開。情報が同じ面から連続的に現れる |
| カード切替 | スワイプ完了 | 現行Webの約350ms spring導入を基準に、次の判断対象へ連続して移る。画面を長く占有する演出はしない |
| カード裏返し | モバイルで検証面を開閉 | 現行380msのY軸回転は補助的な発見操作。表面の詳細入口を代替せず、単独でしか辿れない情報を作らない |
| 成功・競合・失敗 | 決定結果に応じて表示 | 成功・409競合・送信失敗を色だけで混同させない。確定時の触覚、競合時の短い二連フィードバック等は既存挙動に合わせる |

時間は既存実装の観測値を基準として記録した。今後の実装では秒数を機械的に統一するのではなく、タップは即応、詳細は短く連続的、重大操作は進捗が読めることを優先する。動きを減らすOS設定時は移動・拡大を止めても状態と結果を明示する。

### 高度な操作を簡単にするルール

- まずカード単位の標準操作を明示し、一括処理・行選択・値編集などは対象やモードが見えるときだけ提示する。
- 破壊的な一括操作は対象数・対象範囲と結果を確定前に示す。選択状態、適用前プレビュー、取り消しを操作の近くに置く。
- 追加機能は視覚的な混雑を避けて隠すだけでなく、分かるラベルと一貫した入口を付ける。履修が必要な隠しジェスチャーや、一度しか出ない説明に依存しない。
- スワイプとボタン、タッチとキーボードでアクション意味を一致させる。高度な操作を使わなくても基本の判断が完了し、使う人には速度と精度が上がる設計にする。

どの部品も、既存のプロトコル状態を見た目で上書きしない。たとえば409競合を成功色にしない。新しい状態を追加する際は、状態遷移・操作可能性・読み上げ文言まで定義する。

## 5. アクセシビリティと動き

色・動き・触覚は飾りや唯一の伝達手段ではなく、意味を瞬時に伝え、操作の手応えを高める表現手段である。重要な意味は文字・形・状態でも伝え、アニメーションを見なくても操作結果が分かるようにする。

- 主要操作はボタン等でも実行でき、Webではキーボードフォーカスと可視フォーカスを保つ。
- 状態・リスク・差分には読み上げ可能な名前とテキスト表現を用意する。動的な同期結果は適切に通知する。
- 文字拡大、狭い画面、日本語の折返しで主要操作や重要な値が隠れないことを確認する。
- アニメーションは操作の因果関係・状態変化・空間的なつながりを伝える。ジェスチャーへの即時応答、カードの確定、詳細の展開、差分の変化などは精密に演出し、遅延や誤解を招く動きは避ける。`prefers-reduced-motion` 等を尊重し、動きを減らしても意味が失われないようにする。
- 親指優先の配置は片手操作の目標であり、左手利用、キーボード、支援技術を犠牲にする理由にしない。

## 6. Flutter・Webでの一貫性

一致させるものは、**情報の優先順位、意味色、危険度と摩擦の関係、状態名、操作結果、アクセシビリティ上の意味**。OS固有の遷移、シート、フォーカス挙動や入力方式は各プラットフォームに自然な形で実装する。WebをFlutterのピクセルコピーにせず、FlutterをWebのCSS部品移植にもせず、同じ契約をそれぞれのUI部品で満たす。

モバイルのスワイプや触覚を使えない環境でも、同じ判断が明示的な操作で行えること。単純な入口から詳細確認・編集・複数項目の処理など高度な仕事に進める場合も、機能を段階的に見せ、確認・プレビュー・取り消しを一貫させる。オフラインや他端末との競合時も、両クライアントで同じ状態が同じ意味として伝わること。

## 7. 変更時のチェック

新しい画面・部品・状態を作るとき、次を確認する。

- [ ] どのユーザー判断・状態を支えるかが明確で、既存の意味トークンで表せない理由があるか。
- [ ] 重要な結果・影響・可逆性が、装飾やメタ情報より先に読めるか。
- [ ] リスク、操作結果、同期状態を混同せず、色以外の手掛かりもあるか。
- [ ] 通常・処理中・失敗・オフライン・競合・無効のうち該当状態を定義したか。
- [ ] FlutterとWebで同じ意味・情報階層を保ち、各プラットフォームに自然な操作を実現したか。
- [ ] キーボード／タッチ／読み上げ、文字拡大、動きの軽減でも同じ目的を達成できるか。
- [ ] エージェントや外部から来た内容を実行せず、システムUIと区別して描画しているか。
- [ ] 対応するWeb CSS・Flutterトークンと、必要な利用箇所を一緒に更新したか。

## 現状と次の判断

この方針は既存実装を読み解いて整理した設計判断であり、新しい色セット・部品ライブラリ・トークン生成処理を導入する変更ではない。既存ソースは `web/style.css`、`mobile/lib/ui/colors.dart`、`mobile/lib/ui/theme.dart`。まず意味の不一致を新規導入しない運用を優先し、テーマやトークンの機械生成は実装間の反復的なずれが確認された段階で判断する。
