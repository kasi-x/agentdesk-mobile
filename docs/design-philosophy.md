# AgentDesk Frontend Design Philosophy — 洗練の設計原則

> このドキュメントは、AgentDesk のすべての画面（Flutter Mobile / Web Triage UI / ウィジェット等）における
> **フロントエンドのUI・グラフィック・レイアウト・情報設計** の絶対的な指針です。
> プロダクト全体の思想は [philosophy.md](philosophy.md)、プロトコル仕様は [protocol.md](protocol.md) を参照。

---

## 一行で

**余計な情報を極限まで削ぎ落とし、必要な情報を端的に提示し、ドメインに最適なグラフィックで0.5秒の直感認知を実現する。**

---

## なぜフロントエンドの「洗練」が必要なのか

AgentDesk のユーザーは、移動中・作業の合間・片手の親指だけで、数十のエージェントが絶え間なく生成する「判断待ち（Needs Input）」を監督します。

画面が少しでも饒舌であったり、同じ情報が重複していたり、数字や文字の羅列で頭を使わせたりすれば、人間の注意力は一瞬で枯渇し、人は「思考停止でスワイプする（ラバースタンプ）」か「アプリを閉じる」ことになります。

**洗練とは、単に見た目を良くすることではなく、人間の認知負荷を極限までゼロに近づける生存戦略である。**

## 4大設計原則（The Four Pillars）

```
┌────────────────────────────────────────────────────────┐
│ 1. 余計な情報を出さない (Zero Noise)                    │
│    自己申告メトリクスを削る / 画面内の重複表示を完全排除      │
├────────────────────────────────────────────────────────┤
│ 2. 必要な情報を端的に出す (0.5s Cognition)              │
│    結果・影響・可逆性が最前面 / 行動に直結する動詞          │
├────────────────────────────────────────────────────────┤
│ 3. 必要に応じて拡張ビューを用意する (Progressive Disclosure)│
│    カード表は決断、詳細ビューは検証と修正 / 入口の1本化      │
├────────────────────────────────────────────────────────┤
│ 4. 最適なグラフィックとレイアウトを提供する (Domain Native)   │
│    テキストをドメイン専用UIへ昇華 / 親指優先の空間設計      │
└────────────────────────────────────────────────────────┘
```

---

### 原則 1: 余計な情報を出さない（Zero Noise & Single Source of Truth）

1. **エージェントの自己申告メトリクスを排除する**
   - 「Confidence: 94%」のような数字は、ユーザーの判断を誘導するか画面を汚すだけのノイズ。カード表から排除する。
   - 危険度やリスクは、数字ではなく **色（アクセントカラー）・境界線・スワイプの物理的な重さ（摩擦）** という身体性で伝える（原則 P2）。
2. **完全な一箇所表示（Single Source of Truth in View）**
   - **同じ情報は画面内の「唯一の場所」にのみ表示する。** 二重表示は視覚的ノイズであり、ユーザーの視線移動を迷わせる。
   - *例（期限）*: カード表に緊急カウントダウンが出ている間は、詳細ビュー側の期限行を非表示にする。表の表示が消えた場合のみ詳細側に現れる。
   - *例（タイムライン）*: タイムラインのスロット自体に時間が刻まれているなら、その上下に同じ数字の目盛り（ticks）を並べてはならない。
3. **視覚的ノイズ・装飾枠の撲滅**
   - 意味のないブラケット、多重の境界線、過剰な区切り線、装飾のためのアイコンを排除する。
   - 背景色（Surface トークン）の明度差と十分な余白（Padding / Gap）だけで情報のまとまりを表現する。

---

### 原則 2: 必要な情報を端的に出す（0.5s Cognition & Signal-First）

1. **結果・影響・可逆性を最前面に置く（Impact First）**
   - 人間が知るべきは「エージェントがどんな作業をしたか」ではなく、**「承認すると現実の何が変わり、それは後から戻せるか」** である（原則 P3 / P5）。
   - 「承認すると UserA に $120.00 返金」「定例ミーティングを 16:30 に変更」をカード上部に端的に掲げ、可逆性バッジ（`取り消し可` / `取り消し不可`）を添える。
2. **言葉の極限圧縮とタイポグラフィ**
   - システムメッセージの冗長な前置き（「以下の内容でよろしければ…」等）は一切載せない。
   - 主語・動詞・目的語・数値を最短距離で結ぶ。フォントサイズ・ウェイト（Bold / Medium / Caption）の落差で視線の優先順位（Visual Hierarchy）を0.1秒で作る。
3. **アクションラベルの動詞化**
   - 画面上のボタンやスワイプ中のオーバーレイ文言は、汎用の「Approve」「Reject」で済ませず、可能な限り具体的な動詞（「日程を変更する」「返金する $120」「残す」）にする（I-130）。

---

### 原則 3: 必要に応じて拡張ビューを用意する（Progressive Disclosure / 段階的開示）

1. **カード面（表）は決断、拡張ビューは検証と修正**
   - **カード表（第一階層）**: 0.5秒で目を通し、右または左にスワイプして決断できる最小限の情報（要約・インパクト・主要な差分グラフィック）だけに絞る。
   - **詳細ビュー（第二階層）**: なぜその提案になったのかの根拠（Why）、外部由来の引用メール、詳細な前提条件、パラメータの微調整フォームは、カードをめくった先（「詳細を見る / Details」）に用意する。
2. **入口の一本化（No Fragmented Entry Points）**
   - 「Inspect（検証）」と「詳細を見る（Details）」のような、目的が重なる入口を複数並べてはならない。
   - 入口はカードタップまたは「詳細を見る」の1箇所に統一。閲覧はインラインの美しいキーバリューパネルで行い、値の編集（スライダーや日時選択）が必要な場合のみボトムシートを開く。
3. **階層の深さは最大2層まで**
   - カード面（Layer 1） → 詳細パネル/シート（Layer 2）。
   - 3層以上のネストや深い画面遷移はモバイルでのトリアージ速度を殺すため、絶対に作らない。

---

### 原則 4: ドメインに最適なグラフィック、UI、レイアウトを提供する（Context-Native Visualization）

テキスト（文字列）の Diff を漫然と並べるのではなく、**「扱っているデータの実体（日時、金銭、コード、テキスト）」に最も適した固有のグラフィックへ自動昇華（Shape-Shifting）させる。**

#### 1. カレンダー・時間変更（Calendar & Timeline）
- **文字を読ませず、スロットの移動を見せる**:
  - 「2026-10-05 14:00 → 2026-10-05 16:30」と文字を並べるだけでは、前後の文脈（空き時間、重なり）が直感できない。
  - 1日のタイムラインレールの上に、元の予定位置を **ゴーストスロット（点線・透過）** として残し、新しい予定スロットがそこから **滑り込む（Slide Animation）** 視覚グラフィックを提供する。
- **無駄な目盛り（Ticks）を打たない**:
  - スロットの上に `14:00 – 15:00` と時間が刻まれているなら、その下に同じ時刻の目盛線を描かない。スロット自身に時刻と長さを語らせる。

#### 2. 金額・決済（Billing & Money）
- 金額の変動、通貨記号、支払い元から支払い先への矢印をクッキリとしたチップ（Chip）として表示する。
- 100ドル超などの高額・不可逆な操作は、バッジの色（Warning/Critical）を変え、スワイプ閾値を自動で伸ばす（原則 P2 リスク連動の重さ）。

#### 3. 差分表示（DiffBox）
- 汎用テキストの変更は、Before（赤・取り消し線）から After（緑）への変化をミニマルなチップで対比。
- 複数行や unified-diff 形式のものは、等幅フォントと落ち着いた背景コントラストでインライン色分けする（マークアップやWebViewは使わず、プレーンテキストとして安全に描画する）。

#### 4. 外部由来のテキスト（External Quotation）
- メールの本文やPRのコメントなど、AIエージェント外部から持ち込まれた文章は、プロンプトインジェクション対策および文脈分離のため、専用の引用ブロック（`text-external` / Quote Block）スタイルで明確に隔離して描画する（NFR-2.2）。

#### 5. 親指優先の空間設計（Thumb-Zone Layout）
- すべての確定操作（承認、却下、後で、詳細）は、片手で持ったスマートフォンの親指が自然に届く画面下半分に配置する。
- 高リスクカード（Critical + 取り消し不可）では、誤スワイプを防ぐため右スワイプを無効化し、下部アクションバーの「長押し確定リング（Hold-to-confirm）」に自然に誘導する。

#### 6. 視覚と触覚の同期（Visual-Haptic Cohesion）
- スワイプが確定閾値を越えた瞬間の「カチッ（`selectionClick`）」
- 承認確定時の「トン（`mediumImpact`）」、高リスク確定時の「ズシッ（`heavyImpact`）」
- 競合（409 他端末で処理済み）時の「トントン（二連クリック）」
- 視覚のアニメーションと端末の触覚フィードバックをミリ秒単位で完全に同期させ、「画面を凝視しなくても体が判断を覚える」水準を目指す。

## コンポーネント別 洗練のチェックリスト

新しいUIコンポーネントを追加・修正する際は、以下のチェックリストをすべて満たしているか確認すること。

- [ ] **重複のチェック**: この画面の別の場所、または展開前のカード面と同じ情報を重複して表示していないか？
- [ ] **文字数のチェック**: ラベルや説明文をあと30%削れないか？
- [ ] **自己申告のチェック**: エージェントが勝手に算出した「信頼度」「思考ログ」などをカード表に露出させていないか？
- [ ] **グラフィックのチェック**: 文字列の Before/After で済ませず、タイムラインスロットやピルのような直感的な視覚化ができないか？
- [ ] **段階的開示のチェック**: 初見で不要な補助情報（なぜその提案になったか、詳細な出典）が詳細ビューの中に退避されているか？
- [ ] **操作のチェック**: 片手親指の可動域だけで完結しているか？
- [ ] **安全のチェック**: NFR-2.1（HTML/JS evalの排除）を守り、純粋なデータウィジェットとして描画されているか？
